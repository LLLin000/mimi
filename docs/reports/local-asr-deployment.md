## 素材与样本

| 素材 | 内容 | 备注 |
|---|---|---|
| 标准英语片段（38.1s） | 两段母语英语拼接（**说话人 + 节奏变化**），80 词 | 合成素材 |
| 会议音频（4 × 90s） | 真实工作场景多人学术讨论，带中国口音 + 医学术语 | **自有素材，不公开**；报告里只有聚合指标与脱敏的切点片段 |

**已知局限**（采信时请一并考虑）：

- 会议素材规模小（4 段共 6 分钟），切点判定样本为 **9–23 刀/组**
- 术语命中只有 **8 处**，实体准确率的置信区间很宽
- 单机单次条件，未跨机器复测

这些数字**足以支持"哪个方向值得走"**（差异都是数量级的），
**不足以支持精确到小数点的效果声明**。

## 0. 环境

| 项 | 值 |
|---|---|
| mimi | **v1.6.0 + 本地补丁**（见上方"测试基线"） |
| 系统 | Windows 11 家庭版中文版，build 26200（10.0.26200） |
| CPU | Intel Core Ultra 7 255H，**16 核 / 16 线程** |
| 内存 | 31.4 GB（日常空闲 12–18 GB） |
| 显卡 | NVIDIA **RTX 5060 Laptop，8151 MiB**，驱动 610.88；另有 Intel Arc 140T 核显 |
| 磁盘 | D 盘 452 GB（测试期间剩余 13–20 GB） |
| 音频采集 | 按应用采集（锁定到指定播放进程，用来把音乐与测试音频隔离） |
| 日常负载 | 常驻程序（文件索引 / 云同步 / 即时通讯 / 浏览器）常年占 **CPU 45–60%** |

**部署形态**：

```
被测音频（播放进程）
    ↓ 按应用采集
mimi（自定义端点 → ws://127.0.0.1:8791，走 Audio 3.0 协议）
    ↓
自建 ASR worker（服务端断句，16 kHz 直通）
    ↓
本地翻译（Ollama）
```

即：**mimi 一侧没有改动**，只把它自带的「自定义 DashScope ASR」端点指向本地 worker。

## 1. 五项实测发现

### 1.1 `num_threads` 设大反而慢 10 倍、多烧 57 倍 CPU（影响最大的一条）

同一份代码、同一段音频（10 秒），**只改线程数**：

| 线程数 | 墙钟 | **CPU 耗时** |
|---|---|---|
| **1** | **0.51s** | **0.50s** |
| 2 | 1.24s | 4.55s |
| 4 | — | 19.2s |
| **8** | **5.08s** | **28.3s** |
| 16 | — | 67.7s |

换算成整机占用：worker 进程 **561%（约 5.6 核）→ 18%（0.18 核）**。

**原因**：onnxruntime 的线程池在**小推理**上会自旋等待。流式模型每次只解 20ms，
线程同步开销远超计算本身——**线程越多越慢、越烧 CPU**。

这个坑我们踩了两次：第二次是声学端点模型（Smart Turn）的 ONNX 会话只设了
`inter_op_num_threads`、漏了 `intra_op_num_threads`，它默认吃满全部核心，
让 worker 在长轮次里烧到 282%。

> 仓库里目前没有 `num_threads` 相关设置（`grep` 无结果）。
> 如果之后加本地识别后端，**建议从 1~2 开始测**，不要按"核多就设大"的直觉来。

### 1.2 固定静音阈值在真实语音上几乎不触发

真实会议录音（4 段 ×90 秒，带中国口音的英文学术讨论）实测：

| 静音阈值 | 段/90s | CER |
|---|---|---|
| 0.4s | **23.0**（切碎） | 0.2493 |
| 0.6s | 11.8 | 0.2336 |
| 1.2s | 5.8 | 0.2308 |
| **2.0s** | **4.0** | 0.2355 |

**关键**：打印提交原因后发现 **2.0s 这条路径一次都没触发过**——
会议里语速快、停顿短，时长上限内等不到 2 秒静音，
于是分段**完全由时长上限硬切**，切点自然糟糕。

而标准英语（朗读语料）恰好相反：句子间停顿规整，**0.4s 就能按句切**。

**所以不存在一个通用的最优阈值。**

### 1.3 解法：把「触发」与「判决」分开（阈值自适应）

把静音阈值从「到点就切」降格为「**到点开始询问**」，实际切点交给声学端点模型
（[Smart Turn](https://github.com/pipecat-ai/smart-turn)：8.7MB int8、BSD-2、约 10–30ms/次）：

- 静音 ≥ 0.6s → 问它"说完了吗"
- 说完了 → 切；没说完 → 继续等（兜底：硬静音 2.5 倍、时长上限）

**实测（同一批音频，用 LLM 独立判定切点是否为自然句末）**：

| 配置 | **自然句末** | 段数 | 段/分 |
|---|---|---|---|
| 纯时长上限 | 13–27% | 15–22 | 2.5–3.7 |
| 声学判定只管时长上限 | 39% | 23 | 3.8 |
| **0.6s 起点 + 声学逐句判决** | **44%** | **9** | **1.5** |

**用了更短的起点，切出的段反而更少**——说明声学判决拦掉了假断点。
段数从 4.0/分降到 1.5/分，下游翻译调用也随之少一半以上。

**另一个必需的细节**：定稿时要**补足尾部静音**。流式模型的文本永远是
"到目前为止听到的"，只补 0.4 秒会切出 `...investigated docu` 这种**半截词**；
补到 **1.0 秒**后切点质量从 13% 提到 36%。

### 1.4 离线模型在纯静音上会"幻觉"

用离线模型时，纯静音输入会稳定吐出固定套路：

| 语言设置 | 静音上吐出 |
|---|---|
| `language="en"` | `I.` / `The.` / `Yeah.` |
| `language="auto"` | `그.`（韩语）/ `我.` / `我。` |

**根因是判据缺了"有没有语音"这一条**——草稿路径原本只判断"有没有文本"，
于是把幻觉当字幕显示出来了。加一道 `speech_seen` 闸之后，
静音 / 低噪 / 极低噪各 30–50 秒输入**全部 0 输出**。

### 1.5 显示层：`LocalAgreement-2` 治跳字

本地路径的草稿是"重解窗口 → 整段替换"，用户看到的就是**频繁跳字**。
引入 `LocalAgreement-2`（前缀连续两次解码一致才锁定，此后不再改动）后：

| 配置 | **重写率** | 单次最大改写 |
|---|---|---|
| 整段替换 | **50.0%** | 11 词 |
| **LocalAgreement-2** | **14.3%** | **2 词** |

（一个坑：LocalAgreement 必须配"解整轮"。配滑动窗口时每次看到的是不同音频片段，
"前缀"不成立，锁定形同虚设——实测只从 50% 降到 44%。）

## 2. 试过但**无效**的路

同一批真实会议录音上测过，**没有一条改善结果**，其中几条会让结果更差。

### 2.1 后处理纠错：7 种方案全败

思路都是"拿识别结果再让模型修一遍"：

| 方案 | CER 变化 | 备注 |
|---|---|---|
| qwen3:**4b** | **+7.2 ~ +21.7** | 输出失控（143 词输入 → 264 词输出），**换什么提示词都一样** |
| qwen2.5:3b-instruct | +0.017 | 非推理模型，行为最规矩 |
| qwen3:1.7b（关思考） | +0.004 | |
| T5 ASR 后编辑器（专用模型） | +0.017 | |
| 双假设（把第二个 ASR 的输出当证据喂进去） | +0.003 | 仍没跨过中性 |
| ROVER 投票（3 模型融合） | 最好只能**打平** | |

**原因**：残余错误是"听错"，需要**声学证据**；1-best 文本里没有。
文献里的做法（温度采样多假设、候选实体检索）都是在提供"实际说了什么"的证据，
**不是纯文本纠错**。

（ROVER 实现里踩的两个坑也记一下，都会导致错误结论：
**缺 NULL 候选**会让所有模型的多余词被累加，输出比任何单模型都长；
**权重必须按模型分配**而不是按候选序号，否则"大权重"不生效。）

### 2.2 前端降噪：无效

6 个控制变量（含两个降噪模型）测下来**三个假设被推翻**——加降噪并没有让识别变好。

### 2.3 上下文偏置（热词）：该模型开箱不可用

- `hotwords_score` 从 1.5 提到 4.0，**输出一字不差** → 说明上下文图是空的
- 原因：`modeling_unit="bpe"` 需要真正的 BPE 词表做 `bpe_vocab`，
  而 `tokens.txt` 只是 token→id 映射，且该模型发布目录里**没有 `bpe.model`**
- **另外**：只给 `modeling_unit=bpe` 而不给 `bpe_vocab` 会**静默崩进程**
  （不抛异常、无回溯），排查时极易误判成"参数不生效"

### 2.4 在翻译层"补"术语表：层级错了

在翻译层注入术语表，术语准确度确实单向提升（0:5 全胜）。
但实测把**云端转写**直接喂给同一个翻译模型，译文就很好——
**说明翻译层本来就不是瓶颈**，术语表是在补上游 ASR 的错，层级不对。

### 2.5 量化：在 transformers 路径上没用

- ModelOpt 量化的检查点（带 `modelopt_state.pth`）用普通 transformers 加载：
  **慢 97 倍且输出崩坏**（缺 INT8 内核）
- 自己用 bitsandbytes 量化：**慢 4–10 倍、精度不变**——
  量化是**显存受限**时的优化，而这个 0.6B 模型只用 1.6GB / 8.5GB，**根本不缺显存**

### 2.6 模型选型：训练域比参数量重要得多

同一批音频，只换训练数据：

| 模型（训练数据） | CER |
|---|---|
| 仅 LibriSpeech（朗读有声书） | 0.3477 |
| + GigaSpeech（播客 / 自发语音） | 0.2547 |
| 阿里 SenseVoice | 0.2146 |
| Qwen3-ASR 0.6B | **0.1887** |

**一个容易误判的指标陷阱**：某模型 CER 排第二，但**专有名词错误率是最差的**
（28.6% vs 14.3%）。只看 CER 会选错——**实体准确率要单独看**。

### 2.7 顺带：不要用标点判断"句子说完没有"

识别模型会给**任何**片段无脑加句号。我们统计过：归档里 14 段定稿
**100% 以句末标点结尾**，但实际切点里有 `is that in.`、`injection plus.`、
`It was a.` 这种明显切半句的。可用信号是"结尾是不是虚词"或声学端点，**不是标点**。

## 3. 一个部署风险：采集到持续静音时没有任何提示

**静默失败场景**：用户把默认输出设备切成**未连接的蓝牙耳机**
（很常见，比如 AirPods 处于"查找"状态）时，音频被送到一个不存在的地方，
mimi 的回环采集**抓到的全是数字静音**——界面上什么都不显示、也没有错误提示，
看起来就像"识别不工作"。

但日志里其实已经有信号（`mimi_runtime::audio::send_pipeline`）：

```
send_pipeline: audio sent buffers=3800 bytes=1216000 peakDbFS=-90   ← 数字静音
send_pipeline: audio sent buffers=2900 bytes=928000  peakDbFS=-9    ← 正常
```

**建议**：连续若干秒 `peakDbFS` 低于某阈值时，在界面上提示一句
（例如"已采集到持续静音，请检查默认输出设备"）。
这一个提示能省掉很多"识别不工作"的困惑——我们自己就排查了半天。

## 4. 还没试、但值得试的：LiveKit Turn Detector

我们在分段上用的是 [Smart Turn](https://github.com/pipecat-ai/smart-turn)（音频原生 / ONNX / CPU）。
同类的还有 [LiveKit 的 Turn Detector](https://docs.livekit.io/agents/logic/turns/turn-detector/)：

- 同样输出 end-of-turn 置信度，CPU 友好，带 v1-mini 降级
- **有 dynamic 模式**：用会话内的停顿统计**动态调整** min/max delay
  （我们目前是逐句判定，**没有用到跨句统计信息**）
- 有公开的 [End-of-Turn 基准榜](https://livekit.com/benchmarks/eot-bench)

**我们没测它。** 如果要把"语义断点"做成 mimi 的内置能力，
建议把这两个都试一下——比"猜一个静音阈值"这条路清楚得多。

另外有一篇工作**在 Qwen3-ASR-0.6B 上加 LoRA** 学端到端断点判定
（[Causal Supervision for Turn-Aware Streaming ASR](https://arxiv.org/html/2609.04225v1)），
报告 **边界召回 0.97、中位延迟 0.39s**，论文原话是
"没有任何基于静音超时的方案能达到这个平衡"。如果 mimi 后续要做本地识别，这条路值得看。

## 5. 小结

| 发现 | 结论 |
|---|---|
| **`num_threads`** | 设大反而慢 10 倍、多烧 57 倍 CPU；本地后端建议从 1~2 起测 |
| **断句** | 固定静音阈值在会议语音上**一次都不触发**；改成"短阈值触发 + 声学端点判决"后，切点质量 13%→44%、段数减半 |
| **定稿尾静音** | 流式模型必须补 1.0s 尾静音，否则切出半截词（13%→36%） |
| **幻觉** | 离线模型在纯静音上会吐固定文本；判据必须含"有没有语音" |
| **跳字** | `LocalAgreement-2` 把重写率从 50% 降到 14% |
| **后端处理纠错** | 7 种方案全败——不要在这条路上花时间 |
| **静默失败** | 默认输出设备不可用时采集到全静音且无提示；`peakdBFS` 已在日志里，建议在界面提示 |
| **未尝试** | LiveKit Turn Detector（含 dynamic 模式）、Qwen3-ASR + LoRA 断点判定 |

**口径说明**：切点质量与实体命中用 LLM 独立判定（不用我们自己的启发式，避免循环论证），
部分指标样本较小（切点 9–23 刀/组、实体 8 处），已在正文标注；
所有数字都是本机实测，可从附带脚本复现。
